# 要件定義書: Custom CLI TOTP Authenticator (`vtotp`)

## 1. 概要 (Overview)

特定端末および指定復号鍵が存在する場合のみ実行可能な、**「端末固定（クライアント認証）」および「ポータブル運用」を目的としたマルチプラットフォーム対応CLI型TOTP生成ツール**。

暗号化したTOTPシークレット群（JSON）と復号鍵（AES-256-GCM）を物理的に分離管理し、実行時にメモリ上で復号してワンタイムパスワードを出力する。

---

## 2. 目的・背景 (Background & Objectives)

* **目的:** 外部デバイスに依存せず、特定デバイス・特定鍵アクセス環境でのみ機能するセキュアなクライアント認証環境の構築。
* **背景:**
  * クラウド同期型パスワードマネージャーへの過度な依存を避け、端末上のターミナル環境で高速かつ安全に2FAコードを利用したい。
  * 鍵と暗号化ファイルを分離配置することで、Windows Personal Vault、外部メディア、Linux、macOS 等の異なる環境間でも安全に同一設定を引き継ぎたい。
  * Windows 環境特有のパス扱い（引用符混入や空白パス）でもクラッシュせず、パイプ連携が安全に行える堅牢な CLI を実現する。
  * **配布バイナリの耐タンパー性・リバースエンジニアリング耐性の向上:**
    * 従来の PyInstaller 方式（Python バイトコード同梱）では逆コンパイルが容易であり、クライアント認証ツールの配布形態として脆弱性が残るため、C言語トランスパイル・コンパイル方式（Nuitka）を採用してバイナリの難読化・保護を図る。

---

## 3. 機能要件 (Functional Requirements)

### 3.1 核心機能

1. **TOTPコード生成・表示 (`generate` / `get` / `-g`)**
   * サービス名を受け取り、対応する 6 桁の TOTP コードを出力する。
   * **基本形:** `vtotp generate <service>` / `vtotp get <service>` / `vtotp -g <service>`
   * **省略形:** `vtotp <service>`
     * 第一引数が予約済みサブコマンドと一致しない場合は自動的に `generate` として処理する。
     * サブコマンドと同名のサービス名（例: `init`）を呼び出す場合は明示的にサブコマンド（`get` / `generate`）を付与する。

2. **鍵パスの動的指定・解決優先順位 (`-k` / `--key`)**
   * 復号鍵（`master.key`）の保存先は、以下の優先順位に従って決定する。
     1. コマンドライン引数 (`-k` / `--key PATH`)
     2. 環境変数 (`VTOTP_KEY_PATH`)
     3. 設定ファイル (`~/.vtotp/config.json` 内の `key_path`)

3. **暗号化ストレージの動的指定・解決優先順位 (`--storage`)**
   * 暗号化データファイル（JSON）の保存先は、以下の優先順位に従って決定する。
     1. コマンドライン引数 (`--storage PATH`)
     2. 設定ファイル (`~/.vtotp/config.json` 内の `storage_path`)
     3. 既定パス (`config.json` と同一ディレクトリの `vtotp-secrets.enc`)

4. **多言語対応・表示言語解決優先順位 (`-l` / `--lang`)**
   * CLI 表示メッセージ（ヘルプ、プロンプト、情報、警告、エラー）の言語は、以下の優先順位に従って決定する。
     1. コマンドライン引数 (`-l` / `--lang <en|ja>`)
     2. 環境変数 (`VTOTP_LANG`)
     3. 設定ファイル (`~/.vtotp/config.json` 内の `language`)
     4. OS ロケール環境（`LANG`, `LC_ALL`, OS 既定ロケール判定）
     5. 既定フォールバック言語（`en`）
   * 短縮表記として `-l` をサポートする。
   * 早期英語対応として、まずは英語（`en`）および日本語（`ja`）の2言語を完全サポートする。

5. **複数サービス（マルチアカウント）管理**
   * 複数の TOTP シークレットを 1 つの暗号化ストレージで安全に保持・管理する。

### 3.2 ライフサイクル・データ管理機能

1. **初期化機能 (`init`)**
   * 新規の復号鍵（32バイト AES 鍵）を生成し、空の暗号化ストレージファイルと初期設定ファイルを作成する。
   * 鍵パスは引数（`-k` / `--key`）または対話プロンプトで取得する。
   * 言語設定は引数（`-l` / `--lang`）または対話プロンプトで取得し、`config.json` に保存する（未指定時はOSロケール判定に基づき設定）。
   * 既存の鍵が存在する場合は二段階の破壊的変更警告と確認プロンプトを挟む。
2. **鍵の更新・再暗号化機能 (`rekey`)**
   * 新しい復号鍵を再生成し、既存の暗号化データを旧鍵で復号した上で即座に新鍵で再暗号化して保存する。
   * 旧鍵は最大 3 世代まで `<key_path>.1` 〜 `<key_path>.3` として自動退避する。
3. **登録一覧表示 (`list` / `ls`)**
   * 登録済みのサービス名（Key）および発行者（Issuer）を表示する（シークレット自体は非表示）。
4. **登録データ追加・更新 (`add`)**
   * **シークレット入力経路の限定と `--secret` / `-s` 引数の完全廃止:**
     * コマンドライン引数（`--secret` / `-s`）による平文シークレットの直接受け渡しは、シェル履歴やプロセス一覧・監査ログへの露出リスクがあるため完全に廃止・削除する（後方互換性は維持しない）。
     * **手動実行時（標準経路）:** 対話プロンプト（マスキング入力）を標準の入力経路とし、安全に入力させる（空入力時は安全に処理をキャンセル）。
     * **スクリプト・パイプ連携時:** 自動化や外部ツール連携向けに、標準入力からシークレットを受け取る `--stdin` オプションを提供する。
   * 発行者名は `--issuer` オプションで任意に指定可能とする。
5. **登録データ削除 (`remove` / `rm`)**
   * 指定したサービス名の登録情報を削除する（確認プロンプト、または `-f` / `--force` による即時削除対応）。
6. **設定確認・更新機能 (`config`)**
   * **構文設計（ハイブリッド型）:**
     * トップレベルの予約語（Shorthand Fallback 対象外コマンド）を汚染しないため、独立した更新コマンド（`mod` / `update` 等）は新設せず、`config` 配下に集約する。
     * 将来的な設定項目の増加（鍵パス移動等）に対応可能な業界標準の階層構文（`config set <key> <value>`）を基本設計としつつ、日常的に高頻度で切り替える言語設定向けにショートカット構文（`-l` / `--lang`）を提供する。
   * **確認 (引数なし):**
     * `vtotp config` で現在解決されているマスター鍵パス、暗号化ストレージパス、設定言語、および設定ファイルの解決状態を表示する。
   * **更新 (`config set language <en|ja>` / `config -l <en|ja>`):**
     * `config.json` の言語設定（`language`）を更新・保存する。
     * ショートカット（`-l` / `--lang`）は `config set language <lang>` と等価の動作とする。
     * 本バージョン（v0.2.x）では更新対象を言語設定（`language`）に限定し、既存ユーザーが意図せず英語表記になるのを防ぎ、恒久的に好みの言語を固定できるようにする。
   * *※ 将来の拡張課題 (次回以降検討):* 鍵パス移動（`set key_path`）やストレージパス移動（`set storage_path`）の実ファイル移行を伴う設定変更機能は、アトミック性・整合性検証の検討事項が多いため本バージョンでは対象外とし、次回以降の機能拡張として扱う。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1 セキュリティ・Zero Leakage Rule（秘密情報の完全防衛）

* **暗号化規格:** AES-256-GCM（認証付き対称暗号）を採用し、改ざん検知と機密性を担保する。
* **標準出力・エラー出力の厳密分離:**
  * `stdout`: 他のコマンドへのパイプ渡し（クリップボード連携等）を安全に行うため、生成された 6 桁コードのみを出力する。
  * `stderr`: 残り有効時間バー（プログレスバー）、進捗状況、対話プロンプト、エラーメッセージを出力する。
* **Zero Leakage（秘密情報の露出防止・入力経路の厳格化）:**
  * 通常出力・エラー出力を問わず、平文シークレットや鍵バイト列が画面・ログ・スタックトレースに露出することを厳禁とする。
  * **コマンドライン引数経由のシークレット入力の完全禁止:** CLI 引数（`--secret` / `-s` 等）経由での平文シークレット入力を禁止・排除し、プロセス一覧（`ps`, `Get-Process`）やシェル履歴（`.bash_history`, PowerShell Readline履歴）、EDR/プロセス監査ログからの平文漏洩リスクを根本排除する。
  * シークレットの入力経路は、ターミナル対話入力（マスキング入力）またはパイプ連携向けの標準入力（`--stdin`）のみに限定する。
* **インメモリ秘密情報のスコープ限定と非永続化:**
  * 復号された平文シークレットおよび秘密鍵はディスクに一切永続化せず、必要な処理スコープ内のみで一時的に扱い、処理終了次第速やかに参照を破棄する。
  * *※ 注記（技術的制約とスコープ境界）:* Python インタプリタおよびネイティブ実行環境（Nuitka コンパイル環境を含む）のメモリ管理仕様（ガベージコレクションやイミュータブルオブジェクトの特性等）上、OS・プロセス空間レベルでの完全なインメモリゼロ化を保証するものではない。したがって、プロセス実行中のメモリダンプやデバッガによるインメモリ解析等に対して、完全なメモリ消去・漏洩耐性を保証するものではない。
* **ファイルパーミッション保護（マルチプラットフォーム）:**
  * 秘密鍵ファイルおよび関連一時ファイル作成時、実行ユーザー排他のアクセス権限を設定すること。
  * **Unix系OS:** `chmod 0600`（所有者のみアクセス可能）
  * **Windows環境:** 親フォルダからの権限継承を遮断し、カレントユーザーのみにアクセス権を付与するACL（Access Control List）を適用すること。外部依存ライブラリは追加しない。
    * *※ 注記（特権アカウント・Logon SID の残存許容）:* 親フォルダの継承権限がない場合に OS / トークンの既定 DACL 等から自動付与される特権アカウント（`SYSTEM`, `Administrators`, `OWNER RIGHTS`）および現在のログオンセッションエントリ（Logon SID: `S-1-5-5-...`）の残存は許容する。一般の他ユーザーからのアクセスは完全に遮断されており Zero Leakage 要件を満たすこと、また OS レベルの特権アカウントを無理に除外するとバックアップツール等の運用に支障が出るためである。

### 4.2 堅牢性・Windows パス入力対策

* **引用符・空白の自動正規化:**
  * Windows エクスプローラーの「パスのコピー」等で混入する前後引用符（`"` や `'`）および空白を自動除去する。
  * 不一致クォート（例: `"path'`）や正規化後に空となるパス（`""`, `'   '`）は引数解析レベルで早期に拒否（終了コード 2）する。
* **未処理例外の抑止:**
  * Windows 特有の不正パス記号（`?` や `*` 等）に起因する `[WinError 123]` や OS エラーを捕捉し、Python のトレースバックを出さずに整形されたメッセージを表示して安全に終了する。
* **フェイルセーフ（アクセス権限設定の完全性）:**
  * パーミッション・ACL設定時の OS エラーは例外を無視（pass）せず、処理を安全に中断すること。
  * 鍵ファイル生成・保存時に限定し、USB/外部メディア運用（FAT32/exFAT）を阻害しないため、読み取り時の権限強制は行わないこと。
* **明確な終了コード体系:**
  * スクリプト連携時の判定のため、以下の決定的な終了コードを提供する。
    * `0`: 成功
    * `1`: 一般エラー（ファイル I/O 失敗、重複登録等）
    * `2`: CLI 引数解析エラー
    * `3`: 鍵ファイルが存在しない・不正
    * `4`: 暗号化データの破損・復号失敗
    * `5`: 指定サービスが未登録
    * `6`: TOTP シークレット形式不正（Base32 不正等）
    * `7`: ユーザーによるキャンセル

### 4.3 品質・テスト要件

* **カバレッジ:** 単体テストおよび統合テストにより、100% のテストカバレッジを維持する。
* **静的解析:** `flake8`、`mypy --strict`、`black --check` に適合し、警告ゼロを維持する。

### 4.4 パッケージング・配布形態・バイナリ保護要件 (Binary Protection & Distribution)

1. **バイナリ難読化・C言語コンパイル（Nuitka 採用）**:
   * 従来の PyInstaller（Python バイトコード同梱方式）を完全に廃止すること。
   * Python ソースコードを C 言語へトランスパイルし、C コンパイラによりネイティブ機械語バイナリへコンパイルする **Nuitka** を採用すること。
   * 一般的な Python デコンパイラ（`uncompyle6`, `pycdc` 等）によるソースコード復元を防止し、リバースエンジニアリング耐性を担保すること。

2. **配布形態のハイブリッド提供（案3: Standalone ZIP / Onefile EXE / ソースコード版）**:
   * 利用者の環境（特に SEP/Defender 等のセキュリティ監視強度やディスク I/O 性能）やユースケース（日常的な高速呼び出し vs. 単一ファイル持ち運び）に応じた最適な選択肢を提供するため、以下の 3 形態をサポート・明記すること。
     1. **Standalone 版（ZIP アーカイブ配布）: 【高速・日常利用推奨】**
        * Nuitka の `--standalone` モードでコンパイルされたフォルダ一式（`vtotp.exe`、依存 DLL、Python ランタイム）を ZIP 圧縮した成果物（`vtotp-windows-x64.zip`）。
        * **特徴・起動速度:** 実行時の一時解凍オーバーヘッドが完全にゼロであり、**瞬時（約 0.05〜0.1 秒）に起動**する。
        * **セキュリティ特性:** 一時フォルダ（`%TEMP%`）への動的ファイル展開（ドロッパー的挙動）を行わないため、アンチウイルス（SEP 等）による誤検知リスクが最も低く安全。
        * **推奨対象:** ターミナルから頻繁に呼び出し、PATH を通して快適・爆速で TOTP コードを取得したい常用ユーザー。
     2. **Onefile 版（単一実行ファイル配布）: 【ポータブル・単体ファイル版】**
        * Nuitka の `--standalone --onefile` モードでコンパイルされた単一バイナリ（`vtotp.exe`）。
        * **特徴・起動速度:** 実行時の一時フォルダ展開やセキュリティソフト（SEP/Defender）のスキャン割り込みにより待機時間が発生する。日常的な高速利用には Standalone 版を推奨とし、Onefile 版はポータブルな単一ファイル配布（Nuitka 標準の自己展開動作）として提供すること。
        * **セキュリティ特性:** 実行時に一時フォルダへ DLL 群を展開するため、環境や AV 定義によって検知・スキャンの影響を受けやすい。
        * **推奨対象:** PATH 設定やフォルダ展開を行わず、USB メモリや特定フォルダに単一の `.exe` のみを手軽に配置・持ち運びたいユーザー。
     3. **ソースコード版（Python パッケージ）: 【開発者・マルチプラットフォーム向け】**
        * `pip install -e .` または `pip install .` によりローカルの Python 環境へ直接導入して利用する形態。
        * **特徴・起動速度:** Python インタプリタの通常起動速度（約 0.1〜0.2 秒）で動作。OS やアーキテクチャに依存せず、最新の Python 3.11+ 環境があればどこでも動作する。
        * **推奨対象:** Linux/macOS 環境のユーザー、コードを直接確認・改変したい開発者。

3. **ビルド環境・依存関係**:
   * ビルド環境には適切な C/C++ コンパイラ（Windows: MSVC または MinGW64、Linux: GCC/Clang、macOS: Clang）が整備されていること。
   * `pyproject.toml` のビルド依存関係から `pyinstaller` を削除し、`nuitka`（および必要に応じて `zstandard` 等）へ刷新すること。
   * CI/CD（GitHub Actions `release.yml`）上で自動ビルドおよび両バイナリアーティファクト（Standalone ZIP 版および Onefile EXE 版）の生成・リリースが行えること。

4. **機能等価性と完全性検証（スモークテスト）**:
   * Nuitka によりコンパイルされたバイナリ（Standalone 版および Onefile 版）は、Python 実行時と完全に等価な動作（Zero Leakage、暗号化処理、Windows パス正規化、決定的な終了コード体系）を維持すること。
   * CI/CD パイプライン内で、生成されたバイナリに対するスモークテスト（`--version`、`--help`、`init` 等）を実施し、バイナリの健全性を保証すること。

5. **PE ヘッダーメタデータの明記**:
   * 未署名バイナリにおける不審度（SEP等のレピュテーション判定）を緩和するため、Nuitka ビルド時に Windows PE メタデータ（会社名、製品名、バージョン、ファイル説明文、著作権表示等）をバイナリヘッダーへ明記すること。
   * Windows PE バージョン情報は数値 4 区切り（`X.Y.Z.W`）の形式とし、末尾の第4要素（ビルド番号 / プライベートパート `W`）は常に `0` 固定とすること（例: タグ `v0.2.0` やプレリリース識別子の有無に関わらず `0.2.0.0` に正規化）。

6. **プレリリース（Pre-release）運用と除外申請ライフサイクル（プロモーション方式）**:
   * 配布バイナリ更新時のハッシュ変更に伴う SEP（Symantec Endpoint Protection）等のヒューリスティック誤検知リスクに備え、**Git タグにはプレリリース識別子（`-preview.x` や `-rc.x` 等）を付与せず、最初から正式版タグ（`vX.Y.Z`、例: `v0.2.0`）を発行すること**（プレリリース状態はタグ名ではなく GitHub Release のステータスで管理する）。
   * 新規バージョンタグ発行時、GitHub Actions によるリリース成果物（Standalone ZIP 版、Onefile EXE 版）は自動的に「Pre-release」として公開すること。
   * 各成果物の SHA-256 チェックサムを Release ノートおよびサイドカーファイル（`vtotp.exe.sha256`, `vtotp-windows-x64.zip.sha256`）として添付し、その検証済みバイナリを用いてベンダーへの誤検知除外申請（False Positive Submission）および実機検証を実施すること。
   * SEP で検知解除を確認できた後、バイナリの再コンパイルを行わずに当該リリースを「Latest（正式リリース）」へ昇格（プロモート）させること（`gh release edit <tag> --latest --prerelease=false` または GitHub Web UI）。これにより、再ビルドによるバイナリハッシュ変化とそれに伴う SEP 再検知リスクを完全に排除する。

### 4.5 多言語化設計要件 (Internationalization Architecture)

1. **Python コード内包型・型安全メッセージカタログ**:
   * 外部リソースファイル（`.mo` や `.json` 等）を実行時一時展開する方式は、アンチウイルスのドロッパー検知リスクを誘発するため完全に排除すること。
   * すべての翻訳メッセージは純粋な Python コード（定数辞書構造）として内包し、Nuitka コンパイル時に C 言語の静的構造体としてバイナリへ焼き込むこと。
2. **ゼロ・オーバーヘッド パフォーマンス**:
   * CLI 実行時のディスク I/O や動的パース処理を排除し、インメモリの辞書引き（ナノ秒単位）で解決すること。起動遅延オーバーヘッドをミリ秒未満に抑制すること。
3. **型安全性と対訳網羅テスト**:
   * メッセージキーは `StrEnum`（または定数型）で厳格に定義し、typo を静的解析（`mypy --strict`）で防止すること。
   * 単体テスト（`pytest`）において、サポート対象言語（英語・日本語）間でメッセージキーおよびフォーマット引数（`{path}` 等）の完全一致を検証し、未翻訳・プレースホルダー不一致を 100% 検知すること。
4. **Zero Leakage Rule の徹底遵守**:
   * 多言語化メッセージのフォーマット処理において、平文シークレット、秘密鍵バイト列、暗号文生データ等の秘密情報を含めてはならない。
5. **Core 層と表示層の疎結合化**:
   * ドメイン例外（`exceptions.py`）は直書き文字列への依存を低減し、コンテキスト情報（パス名、サービス名等）を保持した上で、表示言語に応じたローカライズ解決を表示層（`formatter.py` 等）と協調して行うこと。

### 4.6 ドキュメント多言語化要件 (Documentation Internationalization)

1. **ファイル分離方式の採用**:
   * リポジトリルート直下の `README.md` を基準ドキュメントとする。
   * 翻訳版ドキュメントは別ファイルとしてルート直下に配置し、英語版として `README.en.md` を提供する。
2. **相互リンクナビゲーションの設置**:
   * `README.md` および `README.en.md` の冒頭に、互いの言語版への切り替えリンクを設置すること。
     * `README.md`: `[English](README.en.md) | 日本語`
     * `README.en.md`: `English | [日本語](README.md)`
3. **配布形態・実行パフォーマンス特性の明記**:
   * `README.md` および `README.en.md` において、Standalone ZIP 版、Onefile EXE 版、ソースコード版の 3 つの利用形態の特徴（起動速度、SEP/Defender による影響、ポータブル性、推奨ユースケース）を対比表および解説として明記し、ユーザーが環境や用途に合わせて適切な形態を選択できるようにすること。

## 5. CLI設計・コマンド体系

### 5.1 コマンド構文規則（オプション配置ルール）

1. **第一引数の固定原則**:
   * 第一引数は必ず **「予約サブコマンド」** または **「サービス名（省略形 generate）」** とし、オプション（`-l`, `-k`, `--storage` 等）の前置配置（`vtotp [オプション...] <サブコマンド/サービス名>`）は認めない（非サポート）。
   * 例外は単独で実行される情報系オプション（`-h`, `--help`, `--version`）のみとする。
2. **オプションの後置原則**:
   * すべてのコマンドオプション（言語指定 `-l`/`--lang`、鍵指定 `-k`/`--key` 等）は、必ずサブコマンドまたはサービス名の後方に指定する。
   * **正式サブコマンド形式**: `vtotp <サブコマンド> <サービス名> [オプション...]`
     * `SERVICE` はサブコマンド直後の必須位置引数であり、オプションは必ず `SERVICE` の後方に指定する（`vtotp get -l ja github` や `vtotp get --key PATH github` などの前置配置は非サポート・終了コード2）。
     * 例: `vtotp get github -l ja`
     * **`add` コマンド構文:** `vtotp add <SERVICE> [--issuer ISSUER] [--stdin] [-k PATH] [--storage PATH] [-l LANG]`
       * ※ `[--secret SECRET]` は廃止。シークレット入力は対話プロンプト（マスキング入力）または `[--stdin]` による標準入力経由で行う。
     * ※ サービス名を伴わないサブコマンド（`list`, `init`, `config`, `rekey` 等）は `vtotp <サブコマンド> [オプション...]` とする（例: `vtotp list -l en`, `vtotp init -k "PATH" -l ja`, `vtotp config -l ja`）。
   * **省略形形式 (Shorthand Fallback)**: `vtotp <サービス名> [オプション...]`
     * 第一引数が予約サブコマンドでない場合、自動的に `generate <サービス名>` として処理する。
     * 例: `vtotp github -l ja`
     * 例: `vtotp github -k "PATH"`

### 5.2 コマンド実行例

```powershell
# 1. 初回初期化（対話入力または引数指定、言語指定）
$ vtotp init
$ vtotp init -k "C:\Users\...\Personal Vault\master.key" -l ja

# 2. 一覧表示（言語オプション指定例）
$ vtotp list -l en
$ vtotp ls

# 3. コード取得 (省略形・明示形・クリップボード連携)
$ vtotp github -l ja
$ vtotp generate github -k "E:\USB\master.key"
$ vtotp github | Set-Clipboard

# 4. サービス追加（対話入力、--stdin による標準入力パイプ渡し、--issuer）
# 対話入力による追加（マスキング入力）
$ vtotp add github
$ vtotp add aws --issuer Amazon

# 標準入力パイプ渡しによる追加（スクリプト・自動化向け）
$ echo "JBSWY3DPEHPK3PXP" | vtotp add aws --stdin
$ echo "JBSWY3DPEHPK3PXP" | vtotp add aws --issuer Amazon --stdin

# 5. 削除 (rm エイリアス, -f / --force)
$ vtotp remove github
$ vtotp rm github -f

# 6. 鍵更新
$ vtotp rekey

# 7. 設定の確認・更新
$ vtotp config                   # 現在の設定・解決言語を確認
$ vtotp config -l ja             # 言語設定を日本語に更新（ショートカット）
$ vtotp config set language en   # 言語設定を英語に更新（標準構文）
```
